# 3D 场景预演与新管线调研

> 用途：把负责人关心的「codex 类编程智能体 + Blender 生成 3D 场景 → Seedance 出片」，落到 EasyTV 画布的真实能力上，给出可执行的分阶段路线。
> 标注约定：**「已在本仓库核实」**＝本次调研在仓库里读到/跑过，附 `文件:行`；**「外部调研来源、未在仓库内复核」**＝来自主代理交付的外部简报（2026-10-10 核实），仓库内无法证实。
> 约束前提（本轮不破）：不新增 npm 依赖、不改 easytv-api、跟练零消耗（绝不真提交模型任务）。
> 结论一句话：**第一版不做 Blender/Codex，也不做「文本→整场 3D 场景」；第一版做「导演台运镜 → 导出预演帧序列 → 图生视频」— 它全部踩在仓库已有能力上，1–2 周可交付。**

## 一、结论先行

1. 负责人问「是平台还没实现这些能力吗」——分两块答：**已有能力**是导演台（three.js 场景 / GLB 导入 / 机位 / 关键帧运镜 / 截图）、图片 → 视频链、媒体动作、批量提交；**没有的能力**是「按时间轴精确导出 3D 帧序列」和「白模 / 深度控制通道」这两块基建（均已核实的零命中，见 §二）。
2. 推荐顺序（沿外部简报 §七，附本仓库工作量判断）：① 导演台「运镜 → 帧序列 → 图生视频（含运镜自动转 prompt）」；② 深度 / 白模 pass + 结构控制通道抽象；③ 3D 场景 / 资产生成接入导演台；④ 配乐 / 音效节点；⑤ 视频超分 / 补帧；⑥ Blender / Codex 外部链路（长期与企业版，不做第一版）。
3. 为什么：在外部简报里，能对到 API 的模型侧结构控制口径目前只确证了 Seedance 2.5 的「白模控制、绿幕编辑」（**外部调研来源、未在仓库内复核**），第三方 API 是否开放未知——所以产品上必须做成**可插拔控制通道**：有控制图就用控制图，没有就退化成首尾帧 + 运镜提示词，而这条退化路径现在就能做。

## 五、三段式路线

标注口径：**现在就能做**＝不新增平台能力；**需要新接口**＝要新前端模块或服务端契约；**需要新模型能力**＝要外部模型 / 供应商支持。

### 阶段一：导演台「运镜 → 帧序列 → 图生视频」一键链路 ——「现在就能做」

- **目标**：在导演台里把预演直接变成可提交的视频任务：一条运镜路径按镜头导出帧序列（彩色），每镜自动建视频节点并写好运镜 prompt，批量出片。这是外部简报排名的第 1 名，也是唯一不依赖外部供应商的入口。
- **用户流程**：（1）导演台摆好场景（GLB 或资产库资产）；（2）拉一条 2–5 个机位的运镜路径（时长 / 缓动 / 曲线 / hold）；（3）点「导出预演」，选输出（第一版只有彩色）与采样（每镜首尾帧，或每 0.25s 一帧）；（4）帧序列上传后落成图像节点，按镜头分组；（5）每镜自动建 video 节点（首帧 `i2v`、首尾帧 `fl2v`），prompt 由运镜路径自动生成（复用 CAMERA_MOVE_ITEMS 文案 + expandCameraTokens）；（6）批量提交 + 点数预估；（7）出片后按需接媒体动作（高清 / 补帧 / 分离音频 / 拉片 / 重拍）。
- **需要的关键接口或节点形态**：新增一个纯前端「预演导出器」（建议 `app/utils/director/export/preview-frames.ts`，不动 `video-export.ts`）：输入 `DirectorProject + 机位 id + 采样策略`，沿 `evaluateCameraPath` 逐采样点设置 `TresPerspectiveCamera`、渲染、`toDataURL`（preserveDrawingBuffer 已开，可直接读当前帧，不必等下一帧）、`assetApi.upload`；产物按「镜头 → 帧序」落图像节点。节点数据沿用现有字段（content / assetId / prompt / params），必要时加一个 `previewFrame?: { cameraId, index, time }` 标记。接口草案（伪签名，供评审）：

  ```ts
  export type PreviewOutput = 'color'                 // 阶段二再扩 'depth' | 'matte'
  export type PreviewSampling =
    | { mode: 'shot-ends' }                           // 每镜首尾帧（默认，最省）
    | { mode: 'interval', seconds: number }           // 每 N 秒一帧（如 0.25）

  // 纯规划：不碰 DOM，可单测（与 organizer / matrix 的纯逻辑同层）
  export function planPreviewFrames(
    camera: DirectorCameraShot, sampling: PreviewSampling, shots?: ShotRange[],
  ): Array<{ time: number, shotIndex: number, label: string }>

  // 执行器：渲染 + 读像素 + 上传，落图像节点；由页面侧（canvas/director.vue）调用
  export async function exportPreviewFrames(opts: {
    project: DirectorProject, cameraId: string, output: PreviewOutput,
    sampling: PreviewSampling,
    renderAt: (pose: CameraPathPose) => Promise<HTMLCanvasElement>,
    upload: (file: File) => Promise<{ url: string, id: number }>,
  }): Promise<{ frames: Array<{ url: string, assetId: number, shotIndex: number, time: number }> }>
  ```

  采样与落图规则（建议写进导出面板文案）：每镜 ≤6 帧；每镜的第一帧固定取该镜起点姿态、末帧取终点姿态（保证 `fl2v` 可用）；每帧文件名带镜头号与时间（`镜子1-0.00s.png`），落图顺序与镜头顺序一致。

  `planPreviewFrames` 已落在 `app/utils/director/export/preview-frames.ts`：没给镜头范围时，相邻两个运镜节点之间的一段运动就是一镜，末帧取这段走完的时刻（不含 hold）。间隔采样超过 6 帧会抽成 6 帧并保住首尾。同一目录的 `previewShotPrompt` 用运镜词表给每一镜写一句提示词。`preview-move-classify.ts` 从这一镜两端认出推 / 拉、左移 / 右移、抬升 / 下降、左摇 / 右摇、上摇 / 下摇、变焦、环绕、柯克变焦、盘旋抬升 / 下降、滚筒旋转、固定镜头；提示词前面带上由起点 fov 写成的景别和全画幅等效焦段（24mm / 35mm 这类，档位与摄影库一致）。`planPreviewClipGraph` 把这些帧按镜收成一组，组里横排图像和每镜一条视频（一帧走 `i2v`，首尾时刻不同走 `fl2v`，只连第一帧和最后一帧）。时间轴上可以选「每镜首尾帧」或「每 0.25 秒一帧」（一镜最多 6 帧，首尾保住），也可以选彩色、深度或白模。彩色导出按钮在点下去之前就标出大约多少点。「导出预演」按所选采样拨播放头再截图，上传后落到导演台节点右侧；上传落图期间按钮一直占着，避免再点一次叠第二批；进行中可以点取消，截图和未传完的帧都会停。彩色会排视频节点；深度和白模只落图像，不提交生成。控制图进模型仍要等接口。

- **依赖的平台能力**：`camera-path.ts:133`、`capture-shot.ts` 的像素读回口径、`director.vue:264/323` 的落图模板、`canvas-task-inputs.ts:47-56`、`batch.ts:7`、`estimateSpend`（CanvasWorkspace.vue:213）。
- **风险**：同屏多个 TresCanvas 的渲染时序（导出时要等场景加载完）；大分辨率逐帧 toDataURL 的一次性内存；采样密度与素材数量（每 0.25s 一帧 × 时长 = 大量 image 节点，建议首版限「每镜首尾帧」或 ≤6 帧）。
- **工作量**：M（外部简报估 1–2 周，本仓库判断依赖面小、复用充分，可信）。

### 阶段二：深度 / 白模 pass + 结构控制通道抽象 ——「需要新接口；控制图进模型属需要新模型能力」

- **目标**：给预演导出加输出类型 `color | depth | matte`（白模），把控制图作为「结构控制通道」抽象进任务提交：有控制图就用控制图，没有就退化成首尾帧 + 运镜提示词。
- **用户流程**：阶段一流程不变，在「导出预演」里多选输出类型；每镜额外得到一张控制图节点（可选只留控制图 + 一条彩色参考）；提交时按通道组装 inputs——控制图角色若网关不支持，则只发 first_frame + prompt，并在 UI 明示「本模型不支持控制图，已按首尾帧口径提交」。
- **需要的关键接口或节点形态**：前端深度 / 白模已经能在导出时换材质渲一帧，落到图像节点，不建视频、不提交（`app/utils/director/export/preview-pass.ts`）。控制通道进任务提交仍要服务端透传控制图角色（属新接口，需与 easytv-api 另行排期），这轮不做。
- **依赖的平台能力**：three.js 渲染管线（仓库内已有 three，无新增依赖）；模型侧控制能力——外部简报确证「Seedance 2.5 官方页提供白模控制、绿幕编辑」（**外部调研来源、未在仓库内复核**），但第三方 API 是否开放未验证；「深度 / 白模 / 相机轨迹」是 2026 公认控制方向（**外部调研来源、未在仓库内复核**）。
- **风险**：控制图的通道口径（深度归一化、白模材质）与模型侧期望不一致时效果反而变差；renderTarget 基建的性能成本；不同模型能力位需要清单化回落。
- **工作量**：M–L（外部简报估 1–2 周；含服务端透传则更长）。

### 阶段三：3D 场景 / 资产生成接入导演台 ——「需要新模型能力」

- **目标**：文本 / 图片 → 3D 场景或资产（GLB），导入导演台再走阶段一 / 二出片。把「场景创作」从手工摆件扩展为「生成 + 人工调」。
- **用户流程**：在导演台「导入」入口增加「AI 生成场景 / 资产」，填文本或参考图 → 生成 GLB（或分层 mesh）→ 导入场景 → 调机位 → 导出预演。
- **需要的关键接口或节点形态**：导入侧已支持 GLB（`imported-model.ts:2`、`DirectorObjectTree.vue:322`），只差「生成 → 下载 GLB → 走同一导入管线」；需要外部 3D 生成 API（或代理服务）与配额管理。候选：腾讯 HunyuanWorld 1.0（语义分层 3D mesh、可导出）、World Labs Marble（多格式导出、有平台 API）、混元 3D 创作引擎、Meshy（**均为外部调研来源、未在仓库内复核**）。
- **依赖的平台能力**：GLB 导入（已有）+ 导演台场景尺度（1 格 = 1 米，`DirectorViewport.vue:133` 注释）+ 外部 API。
- **风险**：生成资产尺度 / 朝向 / 材质不统一，导入后要补一层「落地对齐」（缩放到人高、贴地）；商用授权与素材版权待核（**外部来源未复核**）；外部 API 稳定性与成本。
- **工作量**：M–L（外部简报估 2–4 周 + 外部对接）。

## 六、第一名落地流程（7 步，逐步标注现状）

1. **导演台摆场景** —— 现在就能做：GLB 导入（`imported-model.ts:2`）或资产库（`schema.ts:37-38` 的 local / library 来源）。
2. **拉运镜路径** —— 现在就能做：机位 + CameraNode / CameraSegment（`schema.ts:112/129`），时间轴编辑已具备。
3. **点「导出预演」选输出与采样** —— 按钮已挂在运镜时间轴上，旁边可选每镜首尾帧或每 0.25 秒一帧，以及彩色、深度或白模。深度和白模只存成图像，不进模型。
4. **沿时间轴精确求值渲染、帧序列落成图像节点** —— 已接上：时间轴「导出预演」按所选采样拨播放头、`toDataURL`、上传，再落到导演台节点右侧。间隔超过 6 帧会抽成 6 帧并保住首尾。
5. **每镜自动建视频节点（fl2v / i2v）并把运镜写进 prompt** —— 已接上：`preview-move-classify.ts` 从路径两端认词，`preview-clip-graph.ts` 排成一帧 `i2v`、首尾帧 `fl2v`。提交口径仍是 `canvas-task-inputs.ts` 的 i2v / fl2v。点这些视频节点的生成才会扣点，导出本身不提交。
6. **批量提交与点数预估出片** —— 现在就能做：`app/api/batch.ts:7` + `estimateSpend`（`CanvasWorkspace.vue:213`）+ 运行队列（`app/composables/useCanvasRunQueue.ts`）。
7. **后接高清 / 补帧 / 分离音频 / 拉片 / 重拍与 BGM** —— 前五项现在就能做（`canvas-media-job.ts:43-60`）；BGM 生成属需要新模型能力（外部简报提到 ElevenLabs Music API，**外部调研来源、未在仓库内复核**）。

## 七、为什么 Blender / Codex 不做第一版

1. **可靠性硬证据**：社区 blender-mcp 能跑任意 Python、多角度截图并内置文生 3D（Tripo / Hunyuan3D / Rodin），但 PairCoder++（arXiv:2607.01883）把 Blender 场景脚本可执行率从 0.20 提到 0.78；The Observability Gap（arXiv:2603.26942）在「整场场景」任务上实测 full-scene success 0%（**均为外部调研来源、未在仓库内复核**）。判定：单资产生成可用，整场可直接开拍的场景仍是 demo 级，不适合当第一版产品主链路。
2. **有更划算的替代来源**：HunyuanWorld 1.0（2025-07 开源、语义分层 mesh）、World Labs Marble、混元 3D 创作引擎、Meshy 等（**外部调研来源、未在仓库内复核**）比「让编程智能体写 Blender 脚本」更可控；Infinigen 适合训练与背景，不适合可控分镜（**外部来源、未复核**）。
3. **仓库侧的现实**：导入侧目前只吃 GLB / GLTF 文件（`imported-model.ts:8`），仓库是纯前端 + 已冻结的 easytv-api，没有跑 Blender 进程的位置；且没有 renderTarget 基建——即使 Blender 出了渲染图，进入产品仍要回到「截图 / 帧序列 → 上传 → 落节点」这条同一条接缝。**先把接缝（阶段一）做对，外部 3D 生成才有插进来的口子。**
4. 结论：Blender / Codex 定位为长期与企业版方向（外部简报 §七 列为第 6 名、数月、高风险），本轮不做。

## 八、明确不做的与理由

| 不做项 | 理由 |
| --- | --- |
| 第一版做 Blender / Codex 链路 | 见 §七：整场成功率 0% 的外部证据 + 仓库无服务端落点，收益与风险倒挂 |
| 「文本 → 整场 3D 场景」直接开拍 | 同上；第一版用「GLB 导入 + 导演台手工摆」替代，场景仍是可控的 |
| 为导出引入 ffmpeg.wasm / 新编码依赖 | 违反「不新增 npm 依赖」；帧序列走 PNG 直传，视频走已有 MediaRecorder 路径 |
| 自建视频超分 / 补帧模型服务 | 需要算力与运维，外部简报也把 SeedVR2 自建列为第 5 名；先用媒体动作里的现成高清 / 补帧 |
| 把 3D 预演做成「实时录屏」当控制信号 | 实时录制帧不精确且不可逐帧；控制通道要的是逐帧确定性的图像 |
| 在画布上直接内嵌第二个 3D 视口做预演 | 当前导演台是独立页面（`/canvas/director`，`app/pages/canvas/index.vue:793`），内嵌两套 three 视口（画布外 + 导演台内）复杂度高、收益低；预演产物以节点形态回画布即可 |
| 改 `video-export.ts` 的「真播一遍」语义 | 它是给用户看运镜参考片的路径，动它会牵连既有验收；新导出器另起文件 |

## 九、与跟练课程如何结合

现状（已在本仓库核实）：四条剧本共用同一副八步骨架（`canvas-practice.ts:580-587` 注释、`:870` 的 PRACTICE_SCRIPTS），确实是「图生视频」同一副骨架；负责人要的「从易到难」与「oiioii 式分镜 / 角色 / 场景引导」，平台侧缺的并不是节点类型，而是**预演链路本身没有可演示的产物**。

- **最适合做高阶引导的一段：阶段一（导演台 → 导出预演 → 出片）**。它是「分镜 / 机位」的真实能力，且演示时可以不消耗点数（回放示例素材 + 失败演练的机制现成，`canvas-practice.ts:22-32`）。
- **这条引导演示什么**：跟练剧本 `preview-export`（高阶「3D 预演出片」）已接上：导演台节点 → 落下预演视频 → 点生成看回放成片。不进导演台拖机位，回放仍用 `clip.mp4`。要点讲「运镜是结构，prompt 只写动作」。
- **需要平台先有什么**（按顺序）：
  1. 阶段一的「导出预演」按钮与帧序列落图（已交付）；
  2. 跟练回放仍用仓库自带的 `clip.mp4`；专属预演帧序列素材以后再补；
  3. 判据不做「拖机位」：用「落下预演视频 → 点生成看回放」两步承载；
  4. 「引导期间画布只读」已是跟练现状（可写沙盒只给 prepare，退出还原）。
- **从易到难的编排建议**：L1 图片 + 视频节点；L2 一稿多版 / 媒体动作；L3 角色 / 场景 / 主体一致性；L4 3D 预演出片（`preview-export` 已上）；L5 白模 / 深度控制出片（依赖阶段二与模型能力）。每级都能复用同一副「判据 + 兜底 + 自动备好 + 回放」引擎，只换剧本数据。

## 十、验证方法（按仓库现有测试约定）

1. **纯逻辑进单测**：`planPreviewFrames` 这类规划函数放纯模块，照 `app/utils/director/camera-path.test.ts` 的方式直测（vitest node 环境，`vitest.config.ts` 只挂 `~` 别名）；采样边界（单镜、0.1s 最短段、hold 段内取末姿态）必须有用例。
2. **接线用源码断言**：组件级照 `app/components/canvas/canvas-practice-components.test.ts:1-12` 的做法（readFileSync + 正则/字符串），锁「导出面板存在、按钮调用了导出器、落图带 previewFrame 标记」这几处最容易漏的接线。
3. **端到端手工验收（无法用现有测试替代）**：浏览器里摆 2 镜运镜 → 导出 → 核对帧数与文件名 → 批量提交 2 条视频任务 → 看运行队列与点数扣减；同时验收「控制图不支持时的回落文案」。
4. 校验命令由主流程统一跑：`npm run typecheck`、`npm test`、`npm run build`（本调研不自行跑全量）。

## 十一、风险与待验证清单

1. Seedance 2.5 白模 / 绿幕能力是否对第三方 API 开放（**外部来源未验证**）；不开放则阶段二只投入「深度 pass 生成 + 控制图存档」，先不做通道提交。
2. 浏览器端深度 pass 与模型侧控制图的口径匹配（归一化、分辨率、白模材质）需要一次端到端试片验证。
3. 帧序列上传成本：每 0.25s 一帧 × 镜长会快速消耗 asset 与节点数；首版限「每镜首尾帧」并在导出面板写明。
4. 导演台场景尺度与人像构图：1 格 = 1 米的口径下，模型出片构图仍可能与预演有差（滚镜 / 焦距感），建议 prompt 里带景别与焦段信息。
5. 外部 3D 生成资产的商用条款与版权（HunyuanWorld / Marble / Meshy 等，**均为外部来源，未复核**）。
6. 平台侧节点规模：配方文案里写明「单个工作流 60 节点、单次合成 ≤24 镜」（`canvas-workflow-presets.ts:328` 的产品口径）——多镜预演铺满时要按批分画布。
