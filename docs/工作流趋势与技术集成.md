## 二、部分集成（能力在，但没暴露成可调项）

| 技术 | 现状 | 缺口 |
| --- | --- | --- |
| 多镜头 / multi_prompt（Kling v3 的逐镜提示词） | 只体现在 `multi-shot` 预设的"一脚本两条链" | 没有"一个视频节点吃多条分镜提示词"的显式参数 |
| 首末帧（first/last frame） | 通用配方「两张图·首帧到尾帧」（`fl2v-first-last`）：两张上传位按连线顺序进同一个 `videoMode: 'fl2v'` 视频（先连的是 first_frame，后连的是 last_frame），5 秒 Kling-2.5，预计 80 点 | 只连一张、或两张是同一素材时，提交会丢掉尾帧；卡片教学句已写明。浏览器在画布 68 上核对过卡片（教学句、16:9 · 5 秒 · 1080P、预计 80 点），没有点卡片，画布仍是原来的三个节点 |
| prompt 增强（Wan/H3 的 prompt expansion） | 对话式生成里有 LLM 写提示词，画布上没有独立开关 | 未做成"提示词增强"节点/按钮 |
| 参考图一致性（subject/reference，防脸漂移） | 通用配方「角色一致性·同一主体出片」（`character-consistency`）和「场景延续·一景两镜」（`scene-continuity`）。场景配方是一张 16:9 首帧扇出近景 9:16 与全景 16:9，预计 171 点。两处都不写死主体编号，生成时 `subjectIds` 作为 `subject_ids` 提交。卡片规格行写「近景 9:16 / 全景 16:9」，不再只显示首帧的 16:9。浏览器在画布 68 上核对过场景卡片，没有点卡片 | 主体库是空的时，落图后还要先去建角色或场景再引用。商品换装换景仍走三路参考图，不走主体 |
| 运镜 / LoRA 类控制 | 有运镜预设（`cameraMove`、`camera` 参数）与视频模式 | LoRA 未接入（网关是否暴露未知） |
| 上采样 / 补帧 | 通用配方「出片后再高清」（`clip-then-hd`）：首帧 → 1080P 成片 → 高清节点（`tag=高清`，`hdParams.resolution=2K`，连线成片 → 高清，提交走 upscale）。卡片规格行写成「预计 91 点（高清另计）」，别的配方仍是「预计 91 点」。浏览器在画布 68 上核对过这两行，没有点卡片 | 高清作业的具体点数仍不在卡片上。图片放大仍是选择条上的立即提交，不进配方。补帧和慢放保持关闭 |

## 三、明确不做（附理由）

| 技术 | 为什么不做 |
| --- | --- |
| 子图 / 编组化工作流、工作流文档 schema 版本化与迁移 | 会动到 `CanvasWorkspace.vue`（5000+ 行、薄测试）的核心回路，收益是"未来的可扩展性"，当前回归风险大于收益 |
| CRDT（Yjs）多人协同编辑画布 | 团队空间当前是"同一画布串行编辑 + 乐观锁冲突提示"，尚无并发编辑诉求 |
| 把 3s/2s 轮询改造成 WebSocket/SSE 作业契约 | 任务面已经稳定（`taskApi.summary` + 节点轮询 + 恢复轮询），改造只降时延不增能力 |
| 复刻 oiioii 的预置 CDN 假素材与 Agent 拟人叙事腔 | 我们的跟练走"回放真实产物 + 可选真跑"，假素材反而降低可信度 |

## 五、维护约定

新增一条趋势集成时，在本表补一行：技术 → 来源 → 落点（文件:行）→ 提交哈希；**未做/不做的也要写在这里并给理由**，避免下次再出现"调研过但说不清落在哪"。
