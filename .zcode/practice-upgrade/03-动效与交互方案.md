另外两条对方案有实质影响的既有事实：

- **程序化写视口不会触发 `moveStart` / `moveEnd`**：Vue Flow 的 `d3Zoom.on("start"/"end")` 都有 `if (!event.sourceEvent) return null` 守卫（`vue-flow-core.mjs:8496-8511`），而 d3-zoom 的 `zoom.transform` 走的是 `.start().zoom().end()` 无 sourceEvent（`node_modules/d3-zoom/src/zoom.js:85-98`）。但 `d3Zoom.on("zoom")` **没有**守卫，它会把 `viewport.value` 写一遍并 `emits.viewportChange` / `emits.move`（`vue-flow-core.mjs:8583-8589`）。→ 结论：**可以拿 `@move-start` 当「用户接管」的干净信号（我们自己的逐帧写入绝不会误触发）**；但每帧都会写一次 `viewport.value`。
- **别用逐帧值做进度基准**：`zoom` 处理器在 `userSelectionActive` 时会被解绑（`vue-flow-core.mjs:8580-8582`），此时 d3 变换生效但 `viewport.value` 不再跟随。补间必须以自己持有的 `current` 为准，不能每帧回读 `opts.viewport.value`。

## (a) 相机补间：纯函数 + rAF，宿主逐帧 `setViewport`

### 取舍：为什么不直接用 `setCenter(..., { duration })`

d3 过渡的优点是零 JS 每帧开销、且用户滚轮/拖拽时 d3 自己会 `.interrupt()` 掉它。放弃它的原因有三条，都跟本功能强相关：

1. d3 过渡跑在 d3 的定时器上，**我们拿不到进度**，也就无法「补间中途被 reveal 重定向」「补间中临时把聚光切换到直落模式」（(b) 要用）。
2. d3 过渡没有「用户接管」回调：`moveStart/moveEnd` 被 sourceEvent 守卫挡住，`transition.on('interrupt')` 不在 Vue Flow 的对外接口里。我们拿不到「补间已死」的信号，状态机会僵在 `tweening=true`。
3. `fitView/setCenter` 的王牌是 `interpolateZoom`（会走一段弧），对纯平移是副作用；且数学全在 d3 里，vitest（node 环境、不挂 DOM）一条都覆盖不了。

所以：**主方案 = 纯函数 + rAF 逐帧写 `opts.setViewport`**；d3 `duration` 留作「只要瞬时位移、不要中断语义」的备选（比如以后做「回到跟练起点」）。

### 逐帧写 `opts.setViewport` 可行吗？——可行，但有四条约束

`opts.setViewport({x,y,zoom})`（`useCanvasPracticeHost.ts:51`）→ Vue Flow `setViewport`（`vue-flow-core.mjs:5662`）→ `transformViewport`（:5617）→ `clampPosition` + `d3Zoom.transform`。因为 `duration` 缺省为 0，`getD3Transition` 不建过渡，**同步执行**；沿途触发一次 `zoom` 事件 → 一次 `viewport.value` 写入 + 两次 emit。这与「用户拖拽平移」走的是同一条路径，**开销等价于一次正常拖动**——产品自己已经在 60fps 下承受它。

约束：
1. **一帧只写一次**。补间循环里禁止再调 `setCenter` / `fitView`，否则一帧两次 `viewport` 写入 + 两次全量派生刷新。
2. **不要同时绑 `@viewport-change` / `@move` 去驱动任何东西**（含 tween 自身）——每帧都会触发，容易成环。要感知「用户接管」就绑 `@move-start`（见上，程序化写入不触发）。
3. 仓库里已有一个 `watch(() => [viewport.value.x, viewport.value.y])`（`CanvasWorkspace.vue:3125`，拖动时清掉角色设计师功能点 Inspector）。它每帧都会跑一次，但开头就是 `if (!canvasCastImageRect.value || !castPanePress) return`，代价可忽略，不用改。
4. `zoom` 恒等：跟练的所有 reveal 都不改缩放（`useCanvasPracticeHost.ts:243` 原样透传 `viewport.value.zoom`），成片居中也只用当前 zoom（:453）。所以补间只需线性插值 x/y，**不需要 `interpolateZoom`**。若以后要改 zoom，再补一条 zoom 的缓动，别顺手加。

### 模块：`app/utils/canvas-viewport-tween.ts`（纯函数，零依赖，node 环境可测）

```ts
export type CanvasViewport3 = { x: number, y: number, zoom: number }

/** 出场缓动：easeOutCubic。t 夹到 [0,1]，t<=0 → 0，t>=1 → 1 */
export function canvasEaseOutCubic(t: number): number

/** 帧率无关的指数趋近系数：k = 1 - 2^(-dtMs / halfLifeMs)。halfLifeMs<=0 → 1（直落） */
export function canvasApproachFactor(dtMs: number, halfLifeMs: number): number

/** 一帧的收敛：current 向 target 靠 k；逐分量。zoom 也走同一条（本功能里恒等） */
export function canvasViewportApproach(
  current: CanvasViewport3,
  target: CanvasViewport3,
  dtMs: number,
  halfLifeMs: number,
): CanvasViewport3

/** from→to 走 t（0..1）的位置，x/y 线性 + easeOutCubic */
export function canvasViewportAt(from: CanvasViewport3, to: CanvasViewport3, t: number): CanvasViewport3

/** 补间时长：160 + 0.25*位移(px)，夹在 [200, 420]；缩放差按 1200px/倍 折算成等效位移 */
export function canvasTweenDuration(
  from: CanvasViewport3,
  to: CanvasViewport3,
  opts?: { minMs?: number, maxMs?: number, msPerPx?: number },
): number

/** 是否已收敛（提前收尾，避免亚像素抖动）：dx|dy < 0.5px 且 dzoom < 0.001 */
export function canvasViewportSettled(a: CanvasViewport3, b: CanvasViewport3): boolean

/** 从「锚点元素矩形 + 舞台矩形 + 内边距」算出要把画布平移多少（把现在 host 里 :224-242 的几何搬出来） */
export function canvasRevealShift(
  anchor: { left: number, top: number, right: number, bottom: number, height: number },
  pane: { left: number, top: number, width: number, height: number },
  pad?: number,
): { dx: number, dy: number }

/** reduced-motion 读一次（可注入 matcher 以便测试）；无 window 时返回 false */
export function prefersReducedMotion(win?: { matchMedia?: (q: string) => { matches: boolean } }): boolean
```

时长取值：默认 **`--st-motion-camera` = 260ms**（`canvasTweenDuration` 对典型 100–400px 位移给出 200–260ms）。DESIGN.md:745 建议的 150–200ms 是给 **hover/focus 状态切换**的（原文 "for hover/focus state transitions"），相机位移是整屏级运动，刻意取更长；这一点要在评审时说清，别被「超过 200ms」当违规。缓动用 `easeOutCubic`（快进慢收，和 `organizeCanvas` 的 d3 默认手感同族）。

### Driver：`app/composables/useCanvasCameraGlide.ts`

```ts
export function useCanvasCameraGlide(opts: {
  viewport: Ref<CanvasViewport3>
  setViewport: (vp: CanvasViewport3) => void
  reducedMotion?: () => boolean
}) {
  return {
    /** 平滑到目标视口；已在飞的重定向（从当前帧位置续走），返回 true=已到达，false=被取消 */
    glideTo(to: CanvasViewport3, o?: { durationMs?: number }): Promise<boolean>
    /** reveal 语义：按 dx/dy 平移（dx/dy 由 canvasRevealShift 给） */
    panBy(dx: number, dy: number, o?: { durationMs?: number }): Promise<boolean>
    cancel(): void
    readonly tweening: Ref<boolean>
  }
}
```

关键实现约束（这几条是这套东西最容易静默做错的地方）：

- **单一补间槽**：`glideTo` 覆盖旧目标，新起点 = 旧补间的**当前插值**，不是 `opts.viewport.value`（理由见 §0 第二条：selection 拖拽期间 `viewport.value` 会停止跟随 d3）。所以 driver 自己持有 `current`。
- **打断规则**：
  - 用户 `@move-start`（拖空白 / 滚轮缩放 / 双指）→ `cancel()`，**接管**：不补回、不续走（用户的意图优先）。
  - `canvasLocked` / 只读跟练期间 `nodes-draggable=false`（`CanvasWorkspace.vue:4581`），节点拖动不会发生；但 `panOnDrag` 仍可能是 `[1]`（中键）或空格平移（`:661-664`），所以 `@move-start` 这条必须有，不能只靠 `nodes-draggable`。
  - **选择节点 / 点节点**（`@node-click`、`@node-drag-start`）→ 也 `cancel()`：reveal 的目的已经达到了（用户自己看到了），继续推镜头是在跟用户抢画面。
  - 退出跟练（`session.active → false`）→ `cancel()` 并且**不写最后一帧**（`useCanvasPracticeHost.exit` 会 `loadGraph` 还原 viewport，见 :139-155；补间若在还原后落地一帧会把视口又挪走）。
  - `reduced-motion` → 直接 `setViewport(to)` 一次，不进 rAF。
- **收尾**：`canvasViewportSettled` 命中就写最后一帧精确值再结束，别让亚像素抖动永远差一点。
- **清理**：`onScopeDispose` / `onUnmounted` 里 `cancelAnimationFrame`；宿主是 composable（`useCanvasPracticeHost`），没有自己的生命周期，所以 driver 要能在 `session.active=false` 时自杀（补间循环每帧检查一次）。

### `revealPracticeAnchor` 要改的三处（都在 `useCanvasPracticeHost.ts:210-246`）

1. `:243` 的 `opts.setViewport({...})` 换成 `glide.panBy(dx, dy)`。
2. `:244-245` 的 `if (measure < 1) nextTick(() => revealPracticeAnchor(...))` 保留，但**补间结束后要再量一次**：`await glide.panBy(...)` 之后再跑一轮 `measure`（把 `measure < 1` 放宽到 `< 2`，或者只在「本轮有位移且刚补间完」时加跑一轮）。原因：`canvasFlowPaneRect()`（`canvas-panel-layout.ts:8-18`）量的是 `.canvas-flow` 的矩形，而对话栏折叠是 240ms 宽度过渡（`canvas.css:4577-4582`）——面板在动时量到的 pane 是过期的，260ms 的补间跑完误差就攒下来了。
3. **补间在飞时不要用「移动中的元素矩形」算 dx/dy**：`revealPracticeAnchor` 既被 `REVEAL_MAX_WAIT_FRAMES` 的 rAF 重试调用（`:216`，等新节点渲染），也被 `measure` 重试调用。相机一动，锚点元素的 `getBoundingClientRect()` 每帧都变，此时算出的 dx/dy 是错的。做法：`glide.panBy` 覆盖旧目标（收敛性是对的：起点=当前插值，目标=当前插值+实测 dx），但**重试路径**（`:216` 那个等渲染的 rAF 重试）必须在 `tweening` 为假时才发起新一轮。这一条是本方案引入的**新 bug 面**，测试要盯。

## (b) 聚光平滑：rAF + 指数平滑

### 循环结构（替换 `CanvasPracticeTour.vue:247-273` 的 `setInterval`）

一个常驻 rAF 循环（`session.active` 期间），但**分级节流**，不是每帧全量 `measure()`：

| 内容 | 频率 | 理由 |
|---|---|---|
| 锚点矩形（`querySelector` + `getBoundingClientRect`） | 每帧 | 1 次 `querySelector` + 1 次 rect，量级 1–3µs，可忽略 |
| 平滑 + 写 `spot.value` | 每帧 | 只写 4 个数字；值没变就不写（见下） |
| 卡片选位 `pickGuideCardPosition` + 平滑 | 每帧 | 纯算术，6 个候选位 × 少量矩形交 |
| **zones（`collectZones`）** | **每 8 帧（≈7.5Hz）** | 10 次 `querySelectorAll`（HARD 4 条 `:140` + SOFT 4 条 `:142` + `[data-guide="inspector"]` `:181` + `.canvas-practice-list` `:183`），每帧跑等于把 400ms 的 25 次/秒抬到 600 次/秒 |
| **`measureList()`** | **每 8 帧** + 切步时一次 | 同上，且它内部还要算碰撞 |
| **`readCardSize()`** | **切步 / ResizeObserver 时**，不进每帧 | `:197-206` 里有一次 `getBoundingClientRect`；ResizeObserver 已经盯着卡片（`:275-283`），每帧再量是重复劳动 |

**未实测**：我没法在浏览器里量这 10 次 `querySelectorAll` 的真实耗时。评估：画布页 DOM 量级在千级节点，`querySelectorAll` 对 4–5 个常用类名各自遍历子树，单次约几十 µs，10 次就是几百 µs/帧——正好吃掉 16.7ms 预算的一两个百分点，属于「不致命但没必要」。落地后请用 Performance 面板录 3 秒「跟练 + 聚光跟随」，看 `measure` 自身时长；如果 < 0.3ms，可以把 zones 也放回每帧。

**必须守的响应式纪律**（否则 rAF 循环会变成 60Hz 的响应式风暴）：
- `spot.value` / `listRect.value` / `win.value` / `zones.value` 都是**整对象替换**，`ref` 的相等性是 `Object.is` → 每帧写新对象必然通知全部依赖。**数值没变就别写**（比较 4 个数字再决定），稳态下（用户没动、相机没动）就真的零写入。
- `zones` 里是**新数组**，签名比较不划算 → 用上面的「每 8 帧才重算」代替逐值比较。
- `listStyle`（`:166-170`）/ `cardStyle`（`:233-245`）是 `computed`，只依赖上面的 ref；只要 ref 不乱写，它们就不重算。

### 指数平滑：系数与半衰期

用帧率无关形式，别用固定系数（120Hz 屏上手感会变）：

```
k = canvasApproachFactor(dtMs, halfLifeMs) = 1 - 2 ** (-dtMs / halfLifeMs)
next.x = cur.x + (target.x - cur.x) * k
```

取值建议：

- **稳态跟随：`halfLife = 90ms`** → 60fps 下单帧 k ≈ 0.121，约 3 个半衰期（270ms）到 95%。与相机补间 260ms 同族，观感一致。
- **相机补间在飞时：`halfLife = 0`（直落）**。这是关键：聚光的目标是「框住这个节点」，相机在动时节点本身在匀速移动，指数平滑会产出**恒定滞后** ≈ `v * halfLife / ln2`。以 300px / 260ms 的位移算 v ≈ 1150px/s，90ms 半衰期 → 滞后 ≈ 150px——聚光框会明显吊在节点后面。所以 driver 暴露 `glide.tweening`，为真时聚光直落（k=1），只保留写值。
- **锚点身份切换（换步 / 换锚点选择器）：`halfLife = 0`（直落）**，或最多少量：换步时旧框滑到新框看起来是「同一个框在飞」，会让人以为还是上一步的对象。**换步 = 换对象 = 直落**；「同一个锚点在动」（页面滚动、面板重排、卡片避让）才用 90ms 平滑。
  - 判定「同一个锚点」：比较 `anchorSelector(step.anchor, view)` 的返回字符串，变了就直落。注意 `anchorSelector` 对 `inspector-*` 会带上节点 id（`canvas-practice.ts:240-249`），同一步内节点被换掉也会变字符串 → 正好符合「换对象」语义。
- **reduced-motion：`halfLife = 0`**（等价于现有的 400ms 轮询但更跟手，瞬时对齐）。

### 锚点消失 / 出现的表现

现在 `spot.value = null`（`:222`）会让模板 `v-if/v-else` 在 `.canvas-guide__spot` 和 `.canvas-guide__mask` 之间硬切（`:340` / `:349`），卡片同时掉回 `{left:'50%', bottom:'28px'}` 兜底位（`:236`），是双跳变。

改法（最小、不新增 DOM 分支）：

- **spot 恒在**，删掉 `v-else` 那条 mask 分支；把 `.canvas-guide__mask` 降级成「首帧还没量过」的占位（或直接给它一个 `is-visible` 类由 `spot===null && !win.width` 驱动）。
- **锚点消失** = 把 spot 的矩形**补间到整个视口**（`{left:0, top:0, width:innerW, height:innerH}`，同样走 (b) 的平滑，halfLife 90ms）。视觉上就是「挖的洞收拢成全屏遮罩」，比硬切自然，也不需要给 box-shadow 做 transition。
- **锚点出现**（新节点渲染完）也是同一个补间：从全屏洞收到节点框，260ms 同族手感。注意新节点是「先无后有」，起始矩形取全视口，别取 `{0,0,0,0}`（会出现一条线扫过去）。
- **卡片避让移位**：`pickGuideCardPosition` 的候选位是离散的，直接写 inline `left/top` 会瞬移，甚至从锚点身上穿过去。做法：给卡片位置也上同一条指数平滑（`halfLife = 110ms`），并且**在位移期间给卡片加 `.is-gliding { pointer-events: none }`**——卡片是 `pointer-events: auto`（`canvas.css:767-779`），滑行途中压住锚点会吞掉用户的一次点击。
- **`v-show` → 类名**：`.is-collapsed` 那套（见 (c)）不受影响。

### reduced-motion 直跳

`halfLife = 0` → k = 1 → 每帧直接等于目标；配合 (d) 的 CSS 令牌归零，卡片 / 清单 / 药丸的过渡也一并消失。这样「降级」是一行配置，不是到处 `if`。

## (c) 卡片 / 清单 / 步骤 / 药丸动效

### 通用两条前提

1. **位置一律走 `transform`，不写 `left/top`**。`.canvas-guide` 是 `position: fixed; inset: 0`（`canvas.css:747-753`），它的坐标系原点就是视口原点 → `pickGuideCardPosition` 给的 `left/top` 与 `translate3d(x, y, 0)` **数值等价**，可以无痛迁移。迁移后：卡片改成 `left: 0; top: 0` + `transform: translate3d(...)`，每帧只动 transform（合成层，不触发布局），spot 也可以顺手一起迁。
   - 坑 1：`cardStyle` 的兜底分支带 `bottom: '28px'`（`:236`），迁 transform 时必须一起清掉，否则 `bottom` 与 `top:0` 打架。
   - 坑 2：**`readCardSize` 的准入条件是 `cardEl.value.style.width` 非空**（`:201`）。迁移时必须继续写 inline `width`，否则卡片尺寸永远停在兜底值 340×250，选位几何整段失效（这条没有任何测试接着，属于静默失效）。

## (d) 全局降级：`prefers-reduced-motion`

**位置**：`app/assets/css/studio-parts/tokens-motion.css` 的末尾，一个块管全部（比在 canvas.css 里逐选择器写 `transition: none` 好得多）：

```css
@media (prefers-reduced-motion: reduce) {
  :root {
    --st-motion-fast: 1ms;
    --st-motion-base: 1ms;
    --st-motion-slow: 1ms;
    --st-motion-camera: 1ms;
  }
}
```
- 用 `1ms` 不用 `0s`：`0s` 在部分浏览器下被当作「没有过渡」，`transitionend` 的行为不一致；`1ms` 保留过渡事件语义（清单折叠之类如果有依赖 `transitionend` 的逻辑，不会断）。
- 覆盖范围：卡片出入场、内容淡入、清单折叠、进度条、图标交叉、打勾变色 —— 全部走令牌 → 一次归零。`@keyframes` 那条（角标）令牌管不到，**必须**在同一块里显式关掉：`.cnode__tag-practice { animation: none }`。
- 既有的局部做法保留不动：`canvas.css:423-427`（`.canvas-edge__flow-g { display: none }`，语义是「直接不画流动边」而非「变快」）、`main.css:213-220`、`layout.css:1229`、`pricing.css:1056`。本块是**新增的、加法式的**，不回改它们。
- **JS 侧**：`prefersReducedMotion()`（见 (a)）在 `useCanvasCameraGlide` 里读一次决定 `halfLife = 0` 还是 90；`matchMedia(...).addEventListener('change')` 可以监听变化，但跟练是一次几分钟的会话，**只在会话开始时读一次**就够了，别为它加一个监听（少一个清理点）。
- 既有先例可抄：`CanvasEdgeFlow.vue:95`、`useTheme.ts:147`、`StudioHeroCarousel.vue:104` 都是 `window.matchMedia('(prefers-reduced-motion: reduce)').matches`，风格一致。

1. `expect(host).toContain('requestAnimationFrame(')`（`canvas-practice-components.test.ts:179`）**和** `'setViewport('`（:181）：只要 `useCanvasPracticeHost` 的 `opts` 类型里还写着 `setViewport: (vp: {...}) => void`（`useCanvasPracticeHost.ts:51`），这个断言就继续通过；把 rAF 挪进 driver 不影响它。**别顺手把 `setViewport` 从 opts 里删掉。**

4. `expect(css).toContain('.canvas-practice-list__bar i')`（:226）与 `toMatch(/\.canvas-guide--practice\s*\{[^}]*z-index:\s*72/)`（:223）：换令牌值时保留选择器和 `z-index: 72`；**别为了写新块把 `.canvas-guide--practice { z-index: 72 }` 合并掉**（`canvas.css:879` 与 `:6438` 已经重复了一份，第三份也别拆散）。
